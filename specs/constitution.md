## 一、项目开发原则

### 1.1 核心价值观

1. **简单优于复杂**
   - 代码要简洁易懂，避免过度设计
   - 优先使用简单方案，复杂方案需充分论证
   - 保持代码可读性，让新人能快速上手

2. **约定优于配置**
   - 遵循项目既定规范和约定
   - 减少不必要的配置项
   - 统一命名规范、目录结构、代码风格

3. **实用优于完美**
   - 解决实际问题优先
   - 避免过度优化和过早优化
   - 迭代改进，持续优化

4. **安全优于便利**
   - 安全考虑优先于使用便利
   - 输入验证、输出编码、权限控制
   - 不信任任何外部输入

### 1.2 开发流程原则

1. **需求先行**
   - 开发前明确需求和验收标准
   - 不理解需求不开始编码
   - 需求变更需评估影响

2. **设计先行**
   - 复杂功能先设计后编码
   - 数据库设计先评审后实施
   - API 设计先文档后实现

3. **测试伴随**
   - 代码未写，测试先行（TDD 理念）
   - 功能完成，测试完成
   - 回归测试通过，功能才算完成

4. **文档同步**
   - 代码变更，文档同步
   - API 变更，文档先行
   - 复杂逻辑，注释说明

### 1.3 代码提交原则

1. **小步提交**
   - 每次提交解决一个问题
   - 提交粒度适中，便于回滚
   - 避免巨型提交

2. **规范提交**
   - 遵循 Conventional Commits 规范
   - 提交信息清晰描述变更内容
   - 关联 Issue 或任务编号

3. **完整提交**
   - 提交包含所有相关文件
   - 不包含临时文件、配置文件
   - 提交前本地编译测试通过

4. **及时提交**
   - 完成功能及时提交
   - 避免长期不提交的分支
   - 每日至少提交一次

## 二、代码规范原则

### 2.1 命名规范

#### 基本原则

1. **见名知意**
   - 名称要准确表达含义
   - 避免缩写（通用缩写除外）
   - 不使用无意义的名称

2. **统一风格**
   - 类名：大驼峰 (PascalCase) - `UserService`
   - 方法/变量：小驼峰 (camelCase) - `getUserById`
   - 常量：全大写下划线 - `MAX_RETRY_COUNT`
   - 数据库表：小写下划线 - `sys_user`

3. **类型暗示**
   - 接口：`IUserService` 或 `UserService`
   - 实现：`UserServiceImpl`
   - 抽象类：`AbstractService`
   - 枚举：`UserStatus`

#### 命名禁忌

```java
// ❌ 错误示例
int d;                    // 无意义
int days;                 // 单位不明确
List<User> list;          // 太泛
void process();           // 处理什么？

// ✅ 正确示例
int retryCount;           // 重试次数
int retryDays;            // 重试天数
List<User> activeUsers;   // 活跃用户列表
void processOrder();      // 处理订单
```

### 2.2 代码结构规范

#### 类结构顺序

```java
public class UserService {
    // 1. 静态常量
    private static final String SALT = "ruoyi";
    
    // 2. 静态变量
    private static Logger logger = LoggerFactory.getLogger(UserService.class);
    
    // 3. 实例变量
    @Autowired
    private UserMapper userMapper;
    
    // 4. 构造方法
    public UserService() {}
    
    // 5. 公共方法
    public User getUserById(Long userId) {}
    
    // 6. 私有方法
    private void validateUser(User user) {}
    
    // 7. getter/setter
}
```

#### 方法长度限制

- **最大行数：** 50 行
- **推荐行数：** 20 行以内
- **超长处理：** 提取为私有方法

#### 嵌套深度限制

- **最大嵌套：** 4 层
- **推荐嵌套：** 3 层以内
- **过深处理：** 使用卫语句、提前返回

```java
// ❌ 错误示例 - 嵌套过深
if (user != null) {
    if (user.getStatus() == 1) {
        if (user.getDept() != null) {
            if (user.getDept().getDeptId() != null) {
                // 业务逻辑
            }
        }
    }
}

// ✅ 正确示例 - 卫语句
if (user == null) return;
if (user.getStatus() != 1) return;
if (user.getDept() == null) return;
if (user.getDept().getDeptId() == null) return;
// 业务逻辑
```

### 2.3 注释规范

#### 必须注释的场景

1. **公共 API 方法**
   ```java
   /**
    * 根据用户 ID 查询用户信息
    * @param userId 用户 ID
    * @return 用户信息
    * @throws UserNotFoundException 用户不存在时抛出
    */
   User getUserById(Long userId);
   ```

2. **复杂业务逻辑**
   ```java
   // 计算用户积分：基础积分 + 活动积分 - 扣除积分
   // 基础积分 = 消费金额 * 积分比例
   // 活动积分 = 活动期间额外奖励
   BigDecimal calculatePoints(Order order);
   ```

3. **魔法数字**
   ```java
   // ❌ 错误
   if (status == 1) {}
   
   // ✅ 正确
   // 1 = 正常状态 (见 UserStatus 枚举)
   if (status == 1) {}
   ```

4. **TODO/FIXME**
   ```java
   // TODO: 后续优化为异步处理
   // FIXME: 存在并发问题，需要加锁
   ```

#### 注释原则

1. **注释解释为什么，而不是做什么**
2. **保持注释与代码同步更新**
3. **避免无意义的注释**
4. **使用中文注释（团队约定）**

### 2.4 异常处理规范

#### 异常使用原则

1. **不吞掉异常**
   ```java
   // ❌ 错误 - 吞掉异常
   try {
       // 业务逻辑
   } catch (Exception e) {
       // 空 catch
   }
   
   // ✅ 正确 - 处理或抛出
   try {
       // 业务逻辑
   } catch (Exception e) {
       logger.error("操作失败", e);
       throw new ServiceException("操作失败");
   }
   ```

2. **不滥用异常**
   ```java
   // ❌ 错误 - 用异常控制流程
   try {
       return list.get(index);
   } catch (IndexOutOfBoundsException e) {
       return defaultValue;
   }
   
   // ✅ 正确 - 先检查
   if (index < list.size()) {
       return list.get(index);
   }
   return defaultValue;
   ```

3. **使用自定义异常**
   ```java
   // 业务异常使用 ServiceException
   throw new ServiceException("用户不存在");
   
   // 参数校验使用 IllegalArgumentException
   throw new IllegalArgumentException("用户 ID 不能为空");
   ```

#### 异常层次

```
Throwable
├── Error (系统错误，不捕获)
└── Exception
    ├── RuntimeException (运行时异常)
    │   ├── IllegalArgumentException
    │   ├── IllegalStateException
    │   └── ServiceException (自定义业务异常)
    └── Checked Exception (受检异常)
        ├── IOException
        └── SQLException
```

### 2.5 日志规范

#### 日志级别使用

1. **ERROR** - 错误级别
   - 系统异常、业务异常
   - 需要立即关注的问题
   ```java
   logger.error("用户登录失败，userId={}", userId, e);
   ```

2. **WARN** - 警告级别
   - 可恢复的异常
   - 不影响系统运行但需要注意
   ```java
   logger.warn("缓存未命中，从数据库查询，key={}", key);
   ```

3. **INFO** - 信息级别
   - 系统运行状态
   - 重要业务流程
   ```java
   logger.info("用户登录成功，userId={}, ip={}", userId, ip);
   ```

4. **DEBUG** - 调试级别
   - 开发调试信息
   - 详细的数据状态
   ```java
   logger.debug("查询参数：{}", params);
   ```

#### 日志规范

1. **使用占位符，不使用字符串拼接**
   ```java
   // ❌ 错误
   logger.debug("用户信息：" + user);
   
   // ✅ 正确
   logger.debug("用户信息：{}", user);
   ```

2. **记录关键上下文信息**
   ```java
   // ❌ 错误 - 信息不足
   logger.error("操作失败");
   
   // ✅ 正确 - 包含关键信息
   logger.error("用户更新失败，userId={}, error={}", userId, e.getMessage(), e);
   ```

3. **敏感信息不记录**
   ```java
   // ❌ 错误 - 记录密码
   logger.info("用户登录，username={}, password={}", username, password);
   
   // ✅ 正确 - 脱敏处理
   logger.info("用户登录，username={}", username);
   ```

## 三、架构设计原则

### 3.1 分层原则

1. **依赖单向**
   - 上层可调用下层，下层不可调用上层
   - Controller → Service → Mapper
   - 禁止跨层调用（Controller 直接调用 Mapper）

2. **职责单一**
   - 每层有明确的职责边界
   - Controller：请求处理、参数校验
   - Service：业务逻辑、事务控制
   - Mapper：数据访问

3. **接口隔离**
   - 层与层之间通过接口交互
   - 便于单元测试和 Mock
   - 便于实现替换

### 3.2 模块划分原则

1. **高内聚**
   - 相关功能放在同一模块
   - 模块内部紧密协作
   - 减少模块内部依赖外部

2. **低耦合**
   - 模块间依赖最小化
   - 通过接口而非实现依赖
   - 避免循环依赖

3. **稳定依赖原则**
   - 不稳定模块依赖稳定模块
   - 业务模块依赖通用模块
   - 通用模块不依赖业务模块

### 3.3 数据库设计原则

1. **三范式基础**
   - 第一范式：字段不可再分
   - 第二范式：非主键完全依赖主键
   - 第三范式：非主键不传递依赖

2. **适度反范式**
   - 为性能可适度冗余
   - 冗余数据需有同步机制
   - 权衡读写比例

3. **命名规范**
   - 表名：`sys_模块_功能`，如 `sys_user`
   - 主键：`表名_id`，如 `user_id`
   - 外键：`关联表名_id`，如 `dept_id`
   - 索引：`idx_字段名`，如 `idx_username`

4. **字段规范**
   - 必须包含：`create_time`, `update_time`, `create_by`, `update_by`
   - 逻辑删除：`del_flag` (0 正常 1 删除)
   - 状态字段：使用 tinyint，注释说明含义

### 3.4 缓存设计原则

1. **缓存策略**
   - 读多写少：适合缓存
   - 实时性要求高：谨慎缓存
   - 数据一致性：考虑缓存更新策略

2. **缓存更新**
   - Cache Aside：先更新数据库，再删除缓存
   - 读写穿透：应用层不感知缓存
   - 异步更新：通过消息队列

3. **缓存穿透/击穿/雪崩**
   - 穿透：布隆过滤器、缓存空值
   - 击穿：互斥锁、永不过期
   - 雪崩：随机过期时间、多级缓存

### 3.5 安全设计原则

1. **最小权限原则**
   - 用户只拥有必要权限
   - 服务只访问必要资源
   - 默认拒绝，按需授权

2. **纵深防御**
   - 多层安全防护
   - 不依赖单一安全措施
   - 假设每层都可能被突破

3. **安全默认**
   - 默认配置是安全的
   - 需要主动开启不安全选项
   - 安全配置集中管理

## 四、安全规范原则

### 4.1 认证安全

1. **密码安全**
   - 密码必须加密存储（BCrypt）
   - 密码长度至少 8 位
   - 密码复杂度要求（大小写 + 数字 + 特殊字符）
   - 定期强制修改密码

2. **Token 安全**
   - JWT Token 设置合理过期时间
   - Token 签名密钥安全存储
   - 支持 Token 刷新机制
   - 登出时 Token 加入黑名单

3. **会话安全**
   - 会话超时自动登出
   - 单用户多端登录控制
   - 敏感操作重新认证

### 4.2 授权安全

1. **权限验证**
   - 所有接口必须验证权限
   - 后端验证不可省略
   - 前端权限仅用于 UI 展示

2. **数据权限**
   - 用户只能访问授权数据
   - 数据范围控制（全部、本部门、仅本人）
   - 越权访问严格禁止

3. **功能权限**
   - 菜单权限控制
   - 按钮权限控制
   - 接口权限控制

### 4.3 输入安全

1. **参数校验**
   - 所有输入必须校验
   - 使用注解校验（@Valid）
   - 自定义校验规则

2. **SQL 注入防护**
   - 使用参数化查询
   - 禁止字符串拼接 SQL
   - MyBatis 使用 #{} 而非 ${}

3. **XSS 防护**
   - 输出编码
   - 输入过滤
   - 使用安全组件

4. **CSRF 防护**
   - 使用 Token 验证
   - SameSite Cookie 属性
   - 验证 Referer

### 4.4 数据安全

1. **敏感数据加密**
   - 身份证号、手机号加密存储
   - 传输使用 HTTPS
   - 日志中脱敏

2. **文件上传安全**
   - 限制文件类型
   - 限制文件大小
   - 文件重命名
   - 存储路径隔离

3. **数据备份**
   - 定期备份数据库
   - 备份验证可恢复
   - 异地备份

### 4.5 审计安全

1. **操作日志**
   - 记录关键操作
   - 记录操作人、时间、IP
   - 记录操作内容、结果

2. **登录日志**
   - 记录登录成功/失败
   - 记录登录 IP、地点
   - 异常登录告警

3. **异常监控**
   - 异常集中收集
   - 异常告警通知
   - 异常分析改进

## 五、性能优化原则

### 5.1 数据库优化

1. **索引优化**
   - 高频查询字段建立索引
   - 避免索引失效场景
   - 定期分析慢查询

2. **SQL 优化**
   - 避免 SELECT *
   - 避免 N+1 查询
   - 使用批量操作

3. **分页优化**
   - 深度分页优化
   - 限制最大页数
   - 游标分页替代

### 5.2 缓存优化

1. **热点数据缓存**
   - 字典数据
   - 配置信息
   - 用户信息

2. **缓存粒度**
   - 避免过大对象
   - 合理设置 TTL
   - 缓存预热

### 5.3 接口优化

1. **减少请求**
   - 接口合并
   - 批量查询
   - 按需加载

2. **减少响应**
   - 字段裁剪
   - 数据压缩
   - 分页限制

3. **异步处理**
   - 耗时操作异步
   - 消息队列解耦
   - 最终一致性

## 六、可维护性原则

### 6.1 代码可读性

1. **清晰命名**
2. **合理注释**
3. **适度拆分**
4. **统一风格**

### 6.2 代码可扩展性

1. **开闭原则**
   - 对扩展开放
   - 对修改关闭

2. **依赖倒置**
   - 依赖抽象不依赖具体
   - 便于替换实现

3. **配置外部化**
   - 可配置不硬编码
   - 环境隔离配置

### 6.3 代码可测试性

1. **单元测试**
   - 核心业务逻辑单元测试
   - 测试覆盖率要求
   - 测试独立可重复

2. **集成测试**
   - 关键流程集成测试
   - 接口测试
   - 端到端测试

## 七、团队协作原则

### 7.1 代码审查

1. **必须审查**
   - 所有代码合并前必须审查
   - 至少一人审查通过
   - 审查意见必须处理

2. **审查要点**
   - 功能正确性
   - 代码规范性
   - 性能影响
   - 安全风险

### 7.2 分支管理

1. **分支策略**
   - main：生产分支
   - develop：开发分支
   - feature：功能分支
   - hotfix：热修复分支

2. **合并规范**
   - 功能完成及时合并
   - 解决冲突后测试
   - 删除已合并分支

### 7.3 知识共享

1. **文档沉淀**
   - 技术方案文档
   - 问题解决方案
   - 最佳实践总结

2. **经验分享**
   - 定期技术分享
   - 代码走查
   - 新人培训
